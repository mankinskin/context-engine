Repository: `memory-kernel` submodule, then `memory-api` submodule, then superproject lockfile.

### Step 1 — kernel: add the traits

In `memory-kernel`, in the module that already defines `InteroperableArtifact`:

- Move the verbatim definitions of `IdentifiableArtifact` and `TraceableArtifact`
  from `memory-api/crates/test-api/src/interoperability.rs`.
- `TraceableArtifact` keeps its `InteroperableArtifact` super-trait bound, which now
  resolves locally.
- Export both from the kernel root alongside `InteroperableArtifact`.
- Keep the doc comments as they are; they are already domain-neutral.

Validate: `cargo test -p memory-kernel`.

### Step 2 — kernel: publish

Commit on the feature branch, rebase onto kernel `main`, fast-forward `main`, push.
The git-URL policy means no downstream crate can compile against the new traits
until this push lands.

### Step 3 — memory-api: reduce test-api to re-exports

`memory-api/crates/test-api/src/interoperability.rs` becomes:

```rust
pub use memory_kernel::{
    InteroperableArtifact,
    IdentifiableArtifact,
    TraceableArtifact,
};
```

`src/lib.rs` line 16 already re-exports all three names from this module, so no
change is needed there and no `test-api` consumer breaks.

The `impl IdentifiableArtifact for ValidationExecution` / `impl TraceableArtifact
for ValidationExecution` blocks in `test-api/src/lib.rs` stay where they are — the
type is local, the trait is now foreign, which the orphan rules permit.

### Step 4 — memory-api: point log-api imports at the kernel

`crates/log-api/src/lib.rs` and `crates/log-api/src/store.rs` currently import the
traits from `test_api`. Change those two import sites to `memory_kernel`.
`crates/log-api/src/lib_tests.rs` and `crates/log-api/src/store_tests.rs` import
the same names and need the same change.

`log-api` keeps its `test-api` dependency for now — `ValidationExecution` and
`ValidationLinks` are still used by the adapters, and removing that edge is ticket
`866049e7`.

Validate: `cargo test -p test-api -p log-api`, then `cargo build --workspace`.

### Step 5 — supermodule lock

Update the superproject `Cargo.lock` to the new kernel commit, then run a
patch-free `cargo build --workspace` (temporarily disable the root `[patch]`
section) and confirm the lock records
`git+https://github.com/mankinskin/memory-kernel?branch=main#<new-sha>`.
Restore the `[patch]` section afterwards.

### Risk

Low. Pure relocation with a compatibility re-export; every call site keeps its
existing path. The only sequencing hazard is Step 3 before Step 2 — `memory-api`
cannot see the kernel traits until the kernel push lands.
