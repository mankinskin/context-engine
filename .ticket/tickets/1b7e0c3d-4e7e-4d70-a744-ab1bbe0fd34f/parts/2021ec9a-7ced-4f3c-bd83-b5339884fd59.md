## Resolved decisions

- **`ActiveWorktree` / `BoardSnapshot::active_worktrees` → forward-port into `memory-kernel`.** It aggregates board entries by worktree path with branch, session ids, agent ids, entry ids and collision status. Those are generic coordination and checkout-safety concerns. Its `ticket_ids` field is an identifier carried by the current board entry model, not the organizing concept; optionally generalize that field when the board API is decoupled from ticket ids.
- **`EntityManifest` ticket/spec methods → move OUT into `ticket-api` / `spec-api`.** They use a generic `extra: BTreeMap<String, Value>` only as backing storage, but the public API is concretely ticket/spec coupled: `SpecRef`, `TicketPart`, `TicketRefEntry`, the `related_specs`, `spec_ids`, and `parts` keys, ticket TOML comments, and synthesized `ce://.../spec/...` URNs. Do not generalize prematurely. A neutral `extra_get<T>` / `extra_set<T>` kernel helper would be a separate, later API.
