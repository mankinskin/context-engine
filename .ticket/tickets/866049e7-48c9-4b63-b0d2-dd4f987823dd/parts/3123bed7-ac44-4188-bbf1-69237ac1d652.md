Prerequisite: ticket `4cbe11d3` has landed, so `log-api` no longer imports the
neutral traits through `test-api`. The only remaining edges are the three adapters.

Repository: `memory-api` submodule only. No kernel change, no extraction.

### Step 1 — give log-api a domain-free constructor

In `memory-api/crates/log-api/src/lib.rs`:

- Keep `ValidationLogLinks` exactly as it is (it holds plain `Vec<String>` id lists).
- Add a plain constructor for it that takes the flattened id collections. This is
  what the removed `From` impls will call through from the test side.
- Replace `ValidationLogCapture::from_execution(...)` with a constructor that takes
  `validation_execution_id: String` plus the already-built `ValidationLogLinks`,
  and the unchanged `kind`, `captured_at`, `media_type`, `locator` arguments.
  The struct already stores the execution id as a `String`, so no field changes.

### Step 2 — delete the three test-domain adapters from log-api

Remove from `crates/log-api/src/lib.rs`:

- `impl From<&ValidationExecution> for ValidationLogLinks`
- `impl From<ValidationLinks> for ValidationLogLinks`
- the `from_execution` body superseded in Step 1

Then drop the `use test_api::{ValidationExecution, ValidationLinks, ...}` import in
`src/lib.rs`, the `test_api` import in `src/store.rs`, and the corresponding
imports in `src/lib_tests.rs` and `src/store_tests.rs`. Any test that constructed
a `ValidationExecution` purely to exercise the adapter moves with the adapter in
Step 3; tests that only need link ids switch to the Step 1 constructor.

Finally remove `test-api` from `crates/log-api/Cargo.toml`.

Validate: `cargo test -p log-api`.

### Step 3 — re-home the adapters on the test side

Place them where both types are visible and the dependency direction is
`test -> log`. Preferred home is the public `test` domain crate (or `test-cli`
until that crate exists), which already depends on `test-api` and `log-api`.

Because `impl From<Local> for Foreign` is rejected by the orphan rules, express
the adapters as free functions rather than trait impls:

- `log_links_from_execution(execution: &ValidationExecution) -> ValidationLogLinks`
- `log_links_from_validation_links(links: ValidationLinks) -> ValidationLogLinks`
- `log_capture_for_execution(...) -> ValidationLogCapture`

Each one performs the same field copy the deleted impls performed, then calls the
Step 1 constructors. Move the adapter tests here alongside them.

### Step 4 — update call sites

`crates/test-cli` already imports `log_api` in `src/args.rs`, `src/handlers.rs`,
and `src/lib.rs`. Any site that relied on `.into()` or `from_execution` switches to
the free functions. `memory-matrix` also depends on `log-api`; check whether it used
either `From` impl and update it the same way if so.

Validate: `cargo test -p log-api -p test-api -p test-cli`, then
`cargo build --workspace`.

### Step 5 — prove the cycle is gone

- `grep -rn "test_api" memory-api/crates/log-api/` returns nothing.
- Inspect the dependency graph (for example `cargo tree -p log-api`) and confirm
  no path reaches `test-api`.
- Record the result against the gate in ticket `e8a5c061`.

### Step 6 — live and format checks

- Run one real `test` CLI command that records a validation execution together with
  a log capture, and capture the output.
- Read back an existing stored `.test` and `.log` record to confirm the on-disk
  format is unchanged.

### Risk

Medium. The change is mechanical, but it touches the boundary between two stores
and removes public `From` impls. Any external caller relying on `.into()` breaks at
compile time rather than silently, which is the desired failure mode. The on-disk
formats are untouched, so no migration is needed.
