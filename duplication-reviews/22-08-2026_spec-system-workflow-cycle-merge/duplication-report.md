## Answers to the three flagged questions

**(a) Do both dossiers describe overlapping views of "the spec system" that should collapse to one concept?**
Yes, substantially. Both dossiers independently document the same underlying facts: the Presentation System spec (`2ccde9ee-85ac-4c87-9601-f6099f5be01c`) as a shared case-study/coordination anchor (exact-id near-duplicates in [duplicate-passages.md](duplicate-passages.md) batches 7, 9, 22, 24), the existing test-api evidence-linking capability (`spec_ids`/`ticket_ids`/`acceptance_criterion_ids`, near-duplicates in batches 4, 13, 14, 16, 19, 20, 22, 23, 28, 29, 30), and the fact that ticket→spec gating does not currently exist (near-duplicates in batches 4, 8, 13, 14, 21, 22, 28, 30, 32). These are the same verified facts about the same system, restated independently by each dossier's own research pass — a strong consolidation candidate.

**(b) Is the ticket-spec-gating-edge concept (Dossier A, file `03-ticket-spec-gating-edge.md`) the same idea as the directed-contract-edge concept (Dossier B, file `05-target-artifact-contract.md`), or genuinely distinct?**
**Genuinely distinct**, despite overlapping vocabulary ("edge", "contract", "gating"). Every worker batch that compared these two files or their surrounding context (batches 8, 13, 14, 21, 23, 28) reached the same conclusion: Dossier B's directed contract edge is a **component-to-component** relationship *within* one specification (`from`/`to`/`criteria`, consumer/provider roles, permits cycles) — a spec-authoring-model concept. Dossier A's ticket-depends-on-spec gating edge is a **ticket-to-spec** relationship at the ticket-schema level (should a ticket be blockable by an unfulfilled spec, replacing/supplementing the current ticket-depends-on-ticket model) — already tracked as [5b50329b Ticket-depends-on-spec gating edge](../../.ticket/tickets/5b50329b-59f3-4a6f-a90e-cbacefdcce48). They operate at different artifact layers and should **not** be merged into one concept; they are two separate, complementary gaps in the same broader system.

**(c) Other overlapping waypoints/artifacts between the two ROADMAP.md files?**
Yes — see [duplicate-passages.md](duplicate-passages.md) batch 22 (F9×F18) and batch 9 (F3×F18): both ROADMAP.md files (1) quote the same Presentation System spec id, (2) present a similarly sequenced task list (document/instruction-file step → presentation-deck step → an explicit ticket for a cross-cutting gap), and (3) independently caution that `[[refs]]`/`spec_refs` are informational only, not gating. Additionally, Dossier B's ROADMAP explicitly names the same ticket ([5b50329b](../../.ticket/tickets/5b50329b-59f3-4a6f-a90e-cbacefdcce48)) that Dossier A's ROADMAP created — this is a real, intentional cross-reference rather than an accidental duplicate, and is the strongest single signal that the two dossiers are already coordinated rather than independently duplicative.
