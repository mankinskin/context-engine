# Delegation-cost benchmark (ticket `10d21210`)

Replay-only benchmark for the `79c4ac3e` delegation-cost epic. This defines
the fixed scenario, the metric set, the determinism statement, and the
numeric thresholds that the sibling tickets listed under "Thresholds" cite
instead of the vague phrase "on a comparable follow-up session."

## Architecture: replay-only (binding decision)

This benchmark does **not** run a live multi-agent orchestration session and
does **not** run repeated live sessions. It is a deterministic replay over
two already-captured, checked-in session event logs:

- `3e9bc20b-4fe8-4996-ae7f-7be32525e429`
- `41966513-a8fa-4b44-98fa-9c57f0437cc0`

Both are real orchestrator sessions (already referenced as evidence in
ticket `10d21210`'s description and in the `tmp/subagent_cost_probe.py`
throwaway analysis that motivated the `b7c61f0e` analyzer). Their inputs —
the orchestrator prompts, the repo state at capture time, and the resulting
tool-call trace — are fixed and fully specified by the checked-in event
logs themselves; there is no further interpretation required to reproduce
them (AC1).

## Baseline artifacts (AC2)

```
.benchmark/10d21210/baseline/
  sessions/3e9bc20b-4fe8-4996-ae7f-7be32525e429/events.json
  sessions/41966513-a8fa-4b44-98fa-9c57f0437cc0/events.json
  delegation_cost_report.json
```

`events.json` is each session's raw hook-event audit trail (schema
`PersistedSessionEvents`), copied verbatim from `.session/sessions/<id>/`.
This is the reference artifact, not each session's `transcript.json`: these
two sessions only ever populated their compacted `messages` turns with
`user`/`assistant` text (see
`crate::hook::transcript::handle_message_event`, which pushes only
`user.message`/`assistant.message` events into `messages`) — the
`tool.execution_start`/`tool.execution_complete` events that carry
sub-agent span, tool-call, and failure signals were recorded solely in the
raw event stream. `transcript.json`/`tool-metrics.json` for both sessions
are therefore empty of tool-call data and were not useful as the reference
artifact.

`delegation_cost_report.json` is the checked-in output of the analyzer
(below), keyed by session id, generated by
`memory-api/crates/session-api/tests/delegation_cost_benchmark.rs`'s
`generate_checked_in_baseline_report` (run once with `--ignored`).

## Metric set — computed by the `b7c61f0e` analyzer (AC3)

All metrics are computed by `session_api::delegation_cost`, not by an
ad-hoc script. Two entry points feed the same tested compute function:

- `compute_delegation_cost_report(&SessionRecord)` — the original,
  turns-based entry point, used for sessions whose `messages` already carry
  tool-call turns.
- `compute_delegation_cost_report_from_events(session_id, &PersistedSessionEvents)`
  — new in this ticket: reconstructs the missing tool-call turns from a raw
  event log using the same `parent_event_id` ancestry rule the live capture
  path uses for `subagent_run_id` attribution, then hands the result to the
  **same** `compute_delegation_cost_report` — no metric logic is
  duplicated. This is the path this benchmark uses, and the path any other
  historical session lacking turn-level tool data must use.

`DelegationCostReport` fields (per session):

| Metric | Field | Description |
|---|---|---|
| Sub-agent count | `subagent_count` | Number of distinct `runSubagent` spans |
| Turns per sub-agent | `subagents[].tool_call_count` | Tool calls issued inside each span |
| Per-tool histogram | `subagents[].tools`, `parent_tools` | Tool name → count, per span and at parent level |
| Cross-agent duplicate reads | `cross_agent_duplicate_reads` | Files read (path-normalized) by >1 distinct sub-agent |
| Cross-agent duplicate commands | `cross_agent_duplicate_commands` | Commands run >2 times in total across sub-agents |
| Path-resolution failures | `path_resolution_failures` | Failed `read_file`/`list_dir` calls |
| Substitutable-shell count | `substitutable_shell_count` | `run_in_terminal` calls headed by `cat`/`head`/`tail`/`grep`/`find`/`ls`/`dir`/`wc`/`sed`/`type`/`more`/`less` (a dedicated tool substitute exists) |
| Exploratory find/ls count | `exploratory_find_ls_count` | Subset of the above headed by `find`/`ls`/`dir` specifically |
| Re-dispatch count | `redispatch_count` | `runSubagent` dispatches sharing `(agent_name, description)` with an earlier dispatch in the session whose span recorded a failure |
| Model distribution | `model_distribution` | Count of delegations per model (`model_used`, falling back to `declared_model`, else `"unknown"`) |
| Tokens + cost per sub-agent | `subagents[].input_tokens`/`output_tokens`/`cache_read_tokens`/`cache_write_tokens`/`cost_usd` | Real per-span totals from `data_json.usage`-derived `event_meta` fields (ticket `9d527ad1`), **not** estimated |

## Non-determinism handling (AC4)

Replay is deterministic by construction: `compute_delegation_cost_report[_from_events]`
is a pure function over a fixed, checked-in input. Run count is 1; reported
spread is 0. There is no model sampling, no live tool execution, and no
wall-clock-dependent branch in the analyzer — the same event log produces
byte-identical JSON on every run. This is not a claim that the *system
being measured* (an orchestrator session) is deterministic; it is a claim
that *replaying an already-captured log through the analyzer* is
deterministic, which is exactly what AC6 exercises.

## AC6: reproducibility proof

`memory-api/crates/session-api/tests/delegation_cost_benchmark.rs::replay_reproduces_checked_in_baseline_report_exactly`
recomputes both reports from the checked-in `events.json` files and asserts
the result equals the checked-in `delegation_cost_report.json` exactly
(structural JSON-value equality). Re-running this test against the
unchanged repo passes every time — the harness measures the system (a
fixed log through a pure function), not run-to-run noise.

## Residual limitation (documented honestly)

This ticket proves the harness is deterministic and reproducible (AC4,
AC6) and defines the metric set and thresholds (AC3, AC5). It does **not**
prove any of the sibling tickets' fixes actually reduce these numbers,
because:

- Replay measures the analyzer over a **fixed** log. It cannot, by itself,
  show a before/after "drop" — that requires a **second**, genuinely
  post-change session capture, replayed through this same harness.
- No live A/B comparison was performed as part of this ticket. Any
  "provisional" data point below is a replay of a real captured session,
  not a controlled live experiment, and is labeled as such.
- At the time this ticket was implemented, no capture existed of a
  delegation-orchestration session (i.e. one containing `runSubagent`
  spans comparable to the two baseline sessions) run *after* the sibling
  fixes (`fb14754e`, `66acb737`, `46d8b25d`, `77eb143b`, `cc3324c9`)
  landed. The current implementer's own active session at the time of
  writing was a single-agent Implement Agent run with no `runSubagent`
  delegations, so it is not a comparable scenario and was **not** used to
  fabricate a before/after data point.

When a post-change delegation-orchestration session is captured, replay it
with:

```bash
# copy the new session's events.json under a new sessions/<id>/ directory,
# then add its id to BASELINE_SESSION_IDS-equivalent tooling, or invoke
# compute_delegation_cost_report_from_events directly against it.
```

and compare its report against the baseline totals table above. Label that
comparison "provisional" until it has been repeated for at least one more
independent post-change capture, since a single post-change session is
still N=1.
